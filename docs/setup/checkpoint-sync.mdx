Without checkpoint sync, a new beacon node replays every block since genesis, which takes days on mainnet. With it, the node downloads a recent finalized state from a beacon node you trust and follows the chain within minutes.

<SetupPicker groups="os net" />

## Before you begin

- A beacon node with an **empty** data directory. Checkpoint sync only applies to a fresh database.
- A connected execution client. See [Connect your execution client](/setup/connect-execution-client/).

## Start the node

<Steps>

1. **Pick a provider.** Use your own synced beacon node, or a public endpoint from the community [checkpoint sync endpoints list](https://eth-clients.github.io/checkpoint-sync-endpoints/). Pick one run by an organization you trust.

2. **Add <Flag name="checkpoint-sync-url" /> to your beacon node command.** From the `consensus` folder, with the layout from [Connect your execution client](/setup/connect-execution-client/):

	<When os="unix" conn="jwt">

	```bash
	./prysm.sh beacon-chain \
	  --{net} \
	  --datadir=$HOME/ethereum/data/{net}/beacon \
	  --execution-endpoint=http://localhost:8551 \
	  --jwt-secret=$HOME/ethereum/data/jwt.hex \
	  --checkpoint-sync-url={checkpoint}
	```

	</When>
	<When os="win" conn="jwt">

	```powershell
	.\prysm.bat beacon-chain `
	  --{net} `
	  --datadir=$HOME\ethereum\data\{net}\beacon `
	  --execution-endpoint=http://localhost:8551 `
	  --jwt-secret=$HOME\ethereum\data\jwt.hex `
	  --checkpoint-sync-url={checkpoint}
	```

	</When>
	<When os="unix" conn="ipc">

	```bash
	./prysm.sh beacon-chain \
	  --{net} \
	  --datadir=$HOME/ethereum/data/{net}/beacon \
	  --execution-endpoint=$HOME/ethereum/data/{net}/execution/geth.ipc \
	  --checkpoint-sync-url={checkpoint}
	```

	</When>
	<When os="win" conn="ipc">

	```powershell
	.\prysm.bat beacon-chain `
	  --{net} `
	  --datadir=$HOME\ethereum\data\{net}\beacon `
	  --execution-endpoint=\\.\pipe\geth.ipc `
	  --checkpoint-sync-url={checkpoint}
	```

	</When>

	{/* Endpoints checked against https://eth-clients.github.io/checkpoint-sync-endpoints/ and their /checkpointz/v1/status, 2026-09-28. */}

3. **Watch the logs.** A successful download looks like this:

	```text
	INFO node: Checkpoint sync - Downloading origin state and block
	INFO checkpoint-sync: Downloaded checkpoint sync state and block. blockRoot=0x… blockSlot=… stateRoot=0x… stateSlot=…
	```

	You can leave the flag in place. On later restarts, the node finds its database and carries on from where it stopped. It logs:

	```text
	Origin checkpoint found in the database, ignoring checkpoint sync flags
	```

</Steps>

## Verify the checkpoint

A broken or malicious provider could hand you a state from the wrong chain. Once the node runs, compare its finalized checkpoint with a second provider that has nothing to do with the first.

<Steps>

1. Ask your node for its finalized checkpoint, and note `data.finalized.epoch` and `data.finalized.root`:

	<When os="unix">

	```bash
	curl -s http://localhost:3500/eth/v1/beacon/states/head/finality_checkpoints
	```

	</When>
	<When os="win">

	```powershell
	curl.exe -s http://localhost:3500/eth/v1/beacon/states/head/finality_checkpoints
	```

	</When>

2. Ask a second provider. Endpoints from the list above report their finalized epoch and root at `/checkpointz/v1/status`:

	<When os="unix">

	```bash
	curl -s {checkpoint2}/checkpointz/v1/status
	```

	</When>
	<When os="win">

	```powershell
	curl.exe -s {checkpoint2}/checkpointz/v1/status
	```

	</When>
	<When>

	You can also open the epoch in a block explorer: `{explorer}/epoch/<EPOCH>`.

	</When>

</Steps>

For the same epoch, the roots must be identical. If the epochs differ, finality has just moved on: query both again. If the roots differ, stop your validator, delete the beacon node's data directory, and sync again from another provider.

## Check that it works

<When os="unix">

```bash
curl -s http://localhost:3500/eth/v1/node/syncing
```

</When>
<When os="win">

```powershell
curl.exe -s http://localhost:3500/eth/v1/node/syncing
```

</When>

Right after the checkpoint sync, `head_slot` starts near the checkpoint slot and `sync_distance` drops quickly. When `is_syncing` is `false`, the node is following the chain, and the logs show a `Synced new block` line for every block. `is_optimistic: true` means the execution client is still syncing; your validators can't do their duties until it catches up.

## Good to know

- **No history before the checkpoint.** A checkpoint-synced node validates fine without old blocks. If you want them anyway, add <Flag name="enable-backfill" />; the node downloads them in the background once it's synced.
- **No internet access to a provider?** Download the checkpoint as files on another machine with `prysmctl checkpoint-sync download`, then start the node with <Flag name="checkpoint-state" /> and <Flag name="checkpoint-block" />. See the [prysmctl reference](/reference/cli/prysmctl/).

## Troubleshooting

**The node ignores the checkpoint, but you wanted a fresh sync.** Prysm logs:

```text
Origin checkpoint found in the database, ignoring checkpoint sync flags
```

The data directory already holds a database. Stop the node and start it once with <Flag name="force-clear-db" />, or point <Flag name="datadir" /> at an empty directory.

**The checkpoint download fails or times out.** Prysm logs:

```text
Error retrieving checkpoint origin state and block
```

The provider is down, rate-limited or unreachable. Try another one from the list.

**The download worked but the node stays behind or has few peers.**
Checkpoint sync only sets the starting point. Peers and sync speed depend on your network setup.
